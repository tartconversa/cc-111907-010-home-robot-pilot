# 扩展资料契约（应用附加，不修改既有来源文件）

初始来源目录 `inputs/` 只读。为了登记维护、复查与人员安排的变化，运营可以向工作目录
**导入**以下记录。导入内容复用相同的时间与来源身份原则：

- 时间均带时区、UTC、区间左闭右开。
- `received` 表示运营获知该事实的时点。若 `received` 晚于某次分析，该事实不得用于那次分析。
- 同一来源身份重复投递相同内容 = 重复，不产生新的业务活动。
- 同一来源身份出现不同内容 = 保留原记录并登记为来源冲突（`source-issues` 可查看），不自动覆盖。
- `maintenance` 允许同一来源身份补交延期更正，旧记录保留，按不可用区间并集处理。
- 导入时点不得早于工作目录当前演练时钟；不能用后来的资料回填更早的分析。

导入文件格式（二选一）：

```json
{"table": "maintenance", "rows": [ ... ]}
```

```json
{"maintenance": [ ... ], "capability_review": [ ... ]}
```

## maintenance（与来源契约相同）

维护窗口可以补交延期记录；同一设备可以有多个维护记录。应用识别维护与已承接服务
重叠的**未开始**安排，并提供改期、转人工、取消三种选择。

## capability_review（新增）

| 字段 | 含义 |
|---|---|
| `id` | 复查记录 |
| `robot` | 设备 |
| `version` | 被复查的能力版本 |
| `task` | 任务 |
| `result` | `pass` / `fail` |
| `effective` | 复查结论生效时点 |
| `received` | 运营获知时点 |
| `note` | 说明，可为空字符串 |

规则：同一设备/版本/任务以 `effective` 最新的一条结论为准。`fail` 在再次复查通过前
阻止机器人主办；设备“恢复健康”本身不会解除复查要求。

## staff_unavailability（新增）

| 字段 | 含义 |
|---|---|
| `id` | 不可用记录 |
| `staff` | 工作人员 |
| `start` | 不可用起点 |
| `end` | 不可用终点 |
| `received` | 运营获知时点 |

该区间从人员班次中扣除，不能用于接管保障或直接办理。

## 新增请求

`requests` 也可以通过导入加入。新请求在导入时进入“已收到”状态，并记录导入时刻为
`received`。它不会自动占据资源，也不会自动成为承诺。

## 履约结果

履约结果由应用内的 `ops fulfil` 登记，而不是来源文件。记录时固化当时的设备与能力版本；
之后更换版本不会把旧事实改算到新版本上。默认只保留事实、不进入证据；添加
`--evidence-used` 才会作为后续资格估计的观测。无论是否撤回授权，已发生的履约事实都会
保留（最小履约事实），但撤回后不再使用该家庭历史做估计。

运营附带在履约记录中的备注只在运营视图可见，不会出现在家庭视图。
